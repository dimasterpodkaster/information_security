# Анализ обмена IKEv2 и трафика ESP

### 1. Для чего нужен указанный протокол?

IKEv2 (Internet Key Exchange version 2) согласует криптографические алгоритмы, устанавливает ключевой материал и аутентифицирует участников IPsec-соединения. В результате создаётся IKE SA для защиты управляющих сообщений и Child SA с параметрами защиты пользовательского трафика, например ESP. В исследуемом дампе узлы - `10.20.2.2` и `10.20.2.1`. Сначала проходят IKE_SA_INIT, затем IKE_AUTH.

### 2. Какая в нем используется аутентификация - 2 сторонняя или 1 односторонняя?

Для IKEv2 предусмотрена двусторонняя аутентификация: стороны проверяют подлинность друг друга в ходе IKE_AUTH (RFC 7296). До расшифрования в дампе видны два сообщения IKE_AUTH, но их содержимое зашифровано, поэтому по одним заголовкам нельзя установить конкретный способ аутентификации или проверить наличие AUTH-полей. Ниже расшифрованные кадры 3 и 4 подтверждают, что в этом обмене AUTH действительно отправили обе стороны.

### 3. Поля и типы криптографических механизмов

В предложениях IKE_SA_INIT стороны согласовали AES-CBC-128, HMAC-SHA-1-96 и HMAC-SHA-1 как PRF. Идентификатор метода обмена ключами равен 35. Размеры Key Exchange Data соответствуют ML-KEM-512: открытый ключ инициатора - 800 байт, ciphertext ответчика - 768 байт.

| Поле | ГПСЧ | Асимметричные криптопримитивы | Симметричные криптопримитивы | Почему |
|---|---|---|---|---|
| SPI | Обычно да, генерируется реализацией |  |  | Идентификатор SA должен быть уникальным. Случайная генерация типична, но RFC требует уникальности SPI, а не конкретного способа его получения. |
| Key Exchange Data | Случайность используется внутри алгоритма | Да: ML-KEM-512 |  | Поле содержит открытый ключ и ciphertext механизма инкапсуляции ключа. Это не классический Diffie-Hellman. |
| Nonce Data | Да |  |  | Случайное значение для свежести обмена и формирования ключей. |
| Initialization Vector (IV) | Да |  |  | Для AES-CBC нужен новый непредсказуемый IV для сообщения. |
| Encrypted&Authenticated |  |  | Да: AES-CBC-128 и HMAC-SHA-1-96 | Нагрузка шифруется симметрично. Целостность обеспечивается отдельным ключевым MAC. |
| Integrity Checksum Data |  |  | Да: HMAC-SHA-1-96 | Это значение симметричного MAC, вычисленное по ключу целостности. |

Уточнение по SPI: по одному дампу нельзя доказать, что конкретное значение получено именно ГПСЧ. Здесь оно отнесено к этой категории как типичное поведение реализации. Требование протокола - уникальность.

## После расшифрования трафика IKE_AUTH

Файл `ikev2_decryption_table` размещён в моей конфигурации Wireshark на macOS: `/Users/dmitriinizovcev/.config/wireshark/ikev2_decryption_table`. Для IKE SA используются SPI инициатора `67718cf83a2fad41` и ответчика `40ed851d4c2f6257`. Таблица задаёт AES-CBC-128 и HMAC-SHA-1-96 с разными ключами для двух направлений.

Проверка установленным Wireshark показывает `Decrypted Data` в кадрах 3 и 4. Обе Integrity Checksum Data имеют статус `[correct]`. Команда проверки: `tshark -r save_keys.pcapng -Y 'frame.number == 3 || frame.number == 4' -V`.

### 1. Какая конкретно в данном случае используется аутентификация?

В обоих AUTH-полях метод равен `2` - `Shared Key Message Integrity Code`. Значит, в этом обмене используется заранее распределённый общий симметричный секрет (PSK), а не сертификаты открытых ключей. Наличие AUTH в обоих кадрах подтверждает двустороннюю аутентификацию. Значение AUTH и внешний Integrity Checksum Data - разные поля с разным назначением: AUTH подтверждает знание общего секрета участником, а HMAC в конце IKE-пакета проверяет целостность самого сообщения.

### 2. К каким типам примитивов относятся расшифрованные поля IKE_AUTH?

| Поле | Тип | Обоснование |
|---|---|---|
| Initialization Vector (IV) | ГПСЧ | Для AES-CBC передаётся непредсказуемое значение, новое для каждого сообщения. |
| Encrypted Data | Симметричный механизм | В таблице ключей указан AES-CBC-128. После его применения TShark показывает внутренние payload-данные. |
| Authentication Data | Симметричный механизм | AUTH method 2 вычисляется с общим PSK и согласованной PRF. Это keyed-проверка знания секрета, а не операция с открытым ключом. |
| Integrity Checksum Data | Симметричный механизм | Это внешний для AUTH HMAC-SHA-1-96, проверенный по отдельному ключу целостности. В кадрах 3 и 4 проверка успешна. |

## Расшифрование ESP

Файл `esp_sa` размещён в `/Users/dmitriinizovcev/.config/wireshark/esp_sa`. Для SPI `0xca013134` запись задаёт направление `10.20.2.1` → `10.20.2.2`, алгоритм шифрования `NULL` и целостность HMAC-SHA-1-96. Для декодирования включены пользовательские параметры Wireshark `esp.enable_encryption_decode` и `esp.enable_authentication_check`.

TShark разобрал ESP в кадрах 5-8: SPI совпадает, номера последовательности ESP - 1-4, и HMAC каждого пакета отмечен `[correct]`. Внутри видны IPv4-пакеты `10.20.2.1` → `10.20.2.2` с ICMP Echo Request. В частности, кадр 8 содержит ESP sequence number 4, ICMP sequence number 2 и 40 байт ICMP-данных.

Хотя Wireshark отображает результат в поле `ESP Decrypted Data`, алгоритм `NULL` не выполняет шифрование. Здесь ESP обеспечивает проверяемую целостность и аутентификацию источника в рамках SA, но не конфиденциальность: нагрузка остаётся читаемой.
